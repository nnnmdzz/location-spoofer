# 定位软刷新与生效诊断

本分支为 WLOC 写入后的体验增加一层 App 侧软刷新与状态诊断，目标是减少每次切换坐标后都手动进入“设置 → 隐私与安全性 → 定位服务”关闭/开启总开关的次数。

## 能力边界

该功能只使用公开 Core Location API 做 best-effort 刷新：

- 写入 WLOC 目标后，绕过 App 内 20 秒新鲜缓存，主动请求新的 `CLLocation` 样本。
- 刷新请求临时使用 `kCLLocationAccuracyHundredMeters`，请求结束后恢复原来的 `desiredAccuracy`。
- fresh request 对时间戳使用更严格的 0.15 秒容差，避免把明显早于本次请求的近期样本直接当成新结果。
- App 从系统设置返回前台后，如果上次状态仍是“缓存待刷新 / 疑似高精度定位占优 / 无样本”，会自动重新检测。

该功能**不能**：

- 通过公开 API 清除 `locationd` 的系统级缓存。
- 自动关闭或开启系统“定位服务”总开关。
- 禁用 GPS/GNSS，或阻止其他 App 请求高精度定位。
- 保证 WLOC 在室外强 GPS 环境下覆盖 Core Location 的最终融合结果。

因此手动关闭/开启定位服务仍保留为 fallback，而不是被宣称为完全自动化。

## 状态分类

`LocationEffectMonitor` 最多进行 3 次 fresh request，并将结果归类为：

### 已生效 `effective`

样本距离目标小于：

```text
max(120m, min(400m, horizontalAccuracy × 4))
```

这给网络定位本身的误差留出空间，同时避免把数公里偏移误判为成功。

### 缓存待刷新 `cachePending`

主要包括：

- 新样本仍明显偏离目标，但精度不足以判断为高精度真实定位。
- 从旧虚拟目标切到新虚拟目标时，新样本仍贴近旧目标。

第二条优先级高于 GPS 判断，因为 WLOC 自身也可能返回 20–25m 的 `horizontalAccuracy`。如果只按“高精度 + 远离新目标”判断，会把旧虚拟坐标缓存误报为 GPS。

### 疑似高精度定位占优 `gpsLikelyDominant`

在首次激活或没有上一虚拟目标可解释时，如果样本明显远离目标且满足以下任一条件：

- `horizontalAccuracy <= 35m`；
- 样本仍贴近激活前的定位样本，且 `horizontalAccuracy <= 80m`。

UI 必须使用“疑似 / 可能”等措辞。该状态是启发式诊断，不能证明样本一定来自 GPS。

### 无样本 `unavailable`

多次 fresh request 都没有拿到满足本次时间窗的新样本。常见原因包括定位授权、已有请求占用、系统暂未产生新 fix 等。

## 触发位置

- APP 本地模式：`LocationActionCoordinator` 写入 WGS-84 成功后启动检测；关闭虚拟定位时清理检测状态。
- 第三方代理模式：`ThirdPartyProxyManager.save` 成功并回读坐标匹配后启动检测；`query` 可恢复持久化目标；`clear` 成功后清理检测状态。
- 测试注入的 fake proxy/requester 不启用共享 monitor，避免单元测试触发真实 Core Location 请求。

## UI

现有“生效说明”页顶部增加“自动刷新与生效检测”区块：

- 正在软刷新（1/3 ~ 3/3）
- 定位已生效
- 系统仍可能使用旧定位缓存
- 疑似高精度真实定位占优
- 暂时没有拿到新的定位样本

后三种状态提供“重新检测”和“刷新定位服务”入口。原有飞行模式 / 定位服务手动步骤继续作为 fallback。

## 真机调参建议

建议至少覆盖以下场景：

1. 中国大陆室内：真实位置 → 境外目标。
2. 境外虚拟位置 A → 境外虚拟位置 B，确认旧虚拟位置不会误报 GPS。
3. 中国大陆虚拟位置 → 境外目标，确认 MapKit 坐标系运行时切换逻辑不受影响。
4. 室外开阔区域，观察高精度真实定位是否被归类为 `gpsLikelyDominant`。
5. 从系统定位服务设置关闭/开启后回 App，确认自动复检。
6. Surge 模式杀掉本 App 后重开，确认 `query` 恢复目标并启动检测。

如果真机数据表明 35m / 80m / 120m 等阈值需要调整，应优先根据日志中的 `距目标米`、`horizontalAccuracy` 和“是否有上一虚拟目标”调参，而不是扩大成功半径掩盖失败。
